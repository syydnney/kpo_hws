# ПОС — Преподавательская оценка студентов

Домашнее задание №2 по «Конструированию программного обеспечения» (ВШЭ). Консольный модуль оценки студентов на **C# / .NET 10** с DDD, облегчённой **Ports and Adapters**, DI и тремя уместными паттернами GoF.

## Быстрый запуск

Требуется .NET 10 SDK.

```bash
dotnet restore POS.sln
dotnet build POS.sln
dotnet test POS.sln
dotnet run --project src/POS.Console
```

Пример сквозного сценария: **1** добавить студента → **3** добавить критерии `Домашняя работа` (max=10, weight=4), `Экзамен` (max=20, weight=6) → **5** выставить оценки (8 и 18) → **8** посчитать итог → **9** экспортировать CSV (`result.csv`). По правилу «отсутствующие = 0» итог равен **86%**, когда обе оценки выставлены. **5** с тем же студентом и критерием исправляет оценку, **6** отменяет. **2, 4, 7** показывают данные. Некорректный ввод и несуществующие номера не приводят к созданию недопустимых оценок.

**Данные хранятся только в памяти:** после закрытия приложения они пропадут. Экспортированные CSV остаются на диске. CSV содержит подробные строки критериев, баллов, весов, выбранную политику и итог.

## Доменные решения / карта DDD

**Ubiquitous Language:** `Student` — студент, `Criterion` — критерий, `Rubric` — рубрикатор, `Evaluation` — выставленная оценка, `Gradebook` — ведомость оценок студента, `ScoreResult` — вычисленный итог.

- **Entity:** `Student` (свой `Id`), `Criterion` (свой `Id`; имя/максимум/вес — характеристики, а не идентификатор). Для учебной задачи критерии неизменяемы после создания, их редактирование не требуется ТЗ.
- **Aggregate roots:** `Rubric` владеет коллекцией критериев и запрещает дубли названий без учёта регистра; `Gradebook` владеет текущими оценками *одного* студента и обеспечивает не более одной актуальной оценки на критерий. Оценки разных студентов не блокируют друг друга единым огромным агрегатом.
- **Value Object:** `Evaluation` — неизменяемое значение «StudentId + CriterionId + Score»; исправление реализовано заменой, отмена — удалением. Нет самостоятельной истории оценивания. `ScoreResult` — вычисляемое неизменяемое значение, **не хранится отдельно**.
- **Инварианты:** `Student` требует непустой идентификатор и ФИО; `Criterion` — непустое имя, `MaxScore > 0`, `Weight > 0`; `EvaluationFactory` создаёт оценку только для критерия из переданного `Rubric` и в диапазоне `0 <= Score <= MaxScore`; конструктор `Evaluation` — `internal`. `Gradebook.Record` повторно проверяет наличие критерия в рубрикаторе, диапазон балла и принадлежность оценки студенту. `GradingService` проверяет, что студент существует. Итог не может выйти за пределы 0–100% при корректном состоянии модели.
- **Repository:** `IStudentRepository`, `IRubricRepository`, `IGradebookRepository` — порты во внутреннем слое `Application`, реализации в `Infrastructure`. Репозиторий **для итога не нужен**: он каждый раз считается по актуальным оценкам и рубрикатору.
- **Domain Service:** `FinalScoreCalculator` в Domain, содержит вычисление взвешенного результата без ссылок на консоль, CSV или файлы.

### Формула итога и допущения

Для критерия `i` с баллом `s_i`, максимумом `m_i`, положительным весом `w_i`:

`100 × [Σ(s_i / m_i × w_i)] / [Σ(учитываемых весов)]`.

Округление результата: до **2 знаков после запятой**, `AwayFromZero`; **баллы могут быть дробными** (`decimal`). Веса — **относительные положительные коэффициенты**, а не обязательно доли, суммирующиеся к 1: знаменатель нормализует их автоматически. Не ограничиваем суммарный вес 1, чтобы критерии можно было добавлять последовательно. Отсутствующие оценки: по умолчанию считаются нулём (знаменатель — сумма весов **всех** критериев). Альтернативная политика рассчитывает процент только по оценённым критериям; при отсутствии оценок возвращает 0% (пометка о числе оценённых критериев присутствует в результате). Пустой рубрикатор не позволяет вычислять итог.

**Сознательные ограничения предметной области:** один курс и один рубрикатор; можно исправить/отменить оценку. Критерии после создания неизменяемы, поэтому нет проблемы пересмотра уже выставленных баллов при уменьшении максимума.

## Архитектура: Ports and Adapters

```text
POS.Domain                         (не ссылается на другие слои)
  Models/ Student, Criterion, Rubric, Evaluation, Gradebook
  Factories/ EvaluationFactory
  Scoring/ FinalScoreCalculator, стратегии, ScoreResult
POS.Application  --> POS.Domain
  Ports/ IStudentRepository, IRubricRepository, IGradebookRepository, IResultExporter
  Services/ CatalogService, GradingService, ReportingService, PosFacade
  Reporting/ StudentReport, GradeRow
POS.Infrastructure --> POS.Application, POS.Domain
  Repositories/ InMemory...Repository
  Export/ CsvResultExporter
POS.Console --> POS.Application, POS.Infrastructure
  ConsoleApp, Program (composition root / регистрация DI)
tests/POS.Tests --> Domain, Application, Infrastructure
```

**Направление зависимостей исходного кода:** `Domain` не знает об остальных; `Application` зависит от `Domain`; `Infrastructure` зависит от внутренних портов; `Console` собирает зависимости в `Program`. Консоль не пишет напрямую в хранилища и не считает баллы. Экспортный формат и файловый ввод/вывод полностью снаружи домена. Репозитории зарегистрированы как `Singleton`, потому что парки данных хранятся в оперативной памяти в течение одного запуска.

**Путь команды:** `ConsoleApp` → `PosFacade` → конкретный application service → порты репозиториев + объекты Domain → реализация репозитория в Infrastructure. Для экспорта: `ConsoleApp` → `PosFacade` → `ReportingService` → `FinalScoreCalculator` → `IResultExporter` → `CsvResultExporter`.

## GoF: ровно по одному паттерну из каждой группы

1. **Порождающий — Factory:** `EvaluationFactory`. Единственная публичная точка создания оценки с проверкой допустимого критерия и диапазона балла. Не позволяет случайно создать `Evaluation(12/10)` обычным публичным конструктором. Создание оценки требует знания рубрикатора; это и есть реальная причина фабрики.
2. **Структурный — Facade:** `PosFacade`. Консоль использует одну точку сценариев вместо координации трёх application-сервисов (каталог, оценки, отчёты). Сами сервисы имеют разные ответственности; фасад не содержит бизнес-формул. Это упрощает UI и защищает его от перестановки сценариев.
3. **Поведенческий — Strategy:** `IScoringStrategy`, `MissingAsZeroStrategy`, `GradedOnlyStrategy`. Требование «что делать с отсутствующей оценкой» не определено однозначно; стратегии позволяют выбрать два осмысленных правила из меню, не меняя `FinalScoreCalculator`. Базовый взвешенный расчёт общий; стратегия определяет знаменатель нормализации.

```bash
dotnet test POS.sln

dotnet test tests/POS.Tests/POS.Tests.csproj --collect:"XPlat Code Coverage"
```

Тесты находятся в `tests/POS.Tests`: проверяют валидацию студента и критериев, дубль критериев, недопустимый балл и неизвестный критерий, привязку оценки к студенту, исправление и отмену, обе стратегии, взвешенную формулу, нулевые оценки, сквозной сценарий и CSV-экспорт.

## Границы и возможные изменения на защите

- **JSON вместо памяти:** заменить реализации repository в `Infrastructure`, зарегистрировать их в `Program`; домен и сценарии не зависят от механизма хранения.
- **Несколько курсов:** добавить идентификатор курса и отдельный рубрикатор/ведомости на курс. Сейчас система намеренно однокурсовая.
- **Изменение максимума критерия:** потребует явной политики миграции существующих оценок; сейчас максимум неизменяем.
- **Многопоточность:** in-memory `Dictionary` и выдача живых ссылок на агрегаты не потокобезопасны; в серверном варианте потребуются транзакции, ограничения уникальности и управление конкурентными изменениями.
- **Экспорт иных форматов:** новый адаптер `IResultExporter`, домен менять не нужно.
